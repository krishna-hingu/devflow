# 8.2 First Architectural Principle

We should separate the application into **different responsibilities**.

Conceptually:

```text
                    DEVFLOW
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
      Pages        Components       Data
        │              │              │
        ↓              ↓              ↓
    Route/UI       Reusable UI     Application
    composition    building blocks    data
```

And there are other concerns:

```text
Pages
Components
Layouts
State
Data/API
Utilities
```

But **don't start creating folders yet.**

First understand why these boundaries exist.

---

# 8.3 Pages vs Components

Let's use the Projects screen.

The page conceptually says:

> "I'm the Projects page. I decide what this screen needs."

But individual UI pieces can have their own responsibilities.

For example:

```text
Projects Page
│
├── Page Header
│   ├── Title
│   └── New Project Button
│
├── Search / Filters
│
└── Project List
    └── Project Card
```

So:

### Page

Coordinates the screen.

### Component

Handles a meaningful piece of UI.

This gives us:

```text
Page
 ↓
Components
 ↓
Smaller UI
```

---

# 8.4 But Don't Over-Componentize

This is another important lesson.

We **don't** want:

```text
Projects
 ├── ProjectsTitle
 ├── ProjectsTitleText
 ├── ProjectsTitleContainer
 ├── ProjectsButton
 ├── ProjectsButtonText
 ├── ProjectsListContainer
 ...
```

That's technically "components," but it's terrible architecture.

Instead, component boundaries should exist when they provide a reason:

* Reuse
* Complexity isolation
* Clear responsibility
* Independent behavior
* Easier testing/maintenance

---

# 8.5 Shared vs Feature-Specific UI

This is especially important for DevFlow.

Some components will appear throughout the application.

For example:

```text
Button
Input
Modal
Badge
Card
```

These are **shared UI components**.

Other components are specific to projects:

```text
ProjectCard
ProjectProgress
ProjectTaskList
```

These belong to the **project feature**.

Conceptually:

```text
Shared UI
   │
   ├── Button
   ├── Input
   ├── Card
   └── Badge

Project Feature
   │
   ├── ProjectCard
   ├── ProjectProgress
   └── ProjectTaskList
```

This distinction will matter later when we design our folder structure.

Remember our responsive shell:

Conceptually:

Then:

# 8.7 Data Is Another Responsibility

Now consider this:

The Dashboard wants:

```text
Total projects
Open tasks
Completed tasks
Progress
```

The Projects page wants:

```text
Projects
```

The Project Details page wants:

```text
One project
Its tasks
Activity
```

Analytics wants:

```text
Aggregated information
```

We shouldn't make every component independently invent or manipulate its own copy of the application's data.

Eventually we'll have a data flow something like:

```text

    ↓

    ↓
Application state
    ↓
Pages
    ↓
Components
    ↓

```

For our initial version, the data source can be mock/local data.

Later, when you learn backend development, the same conceptual boundary can evolve toward:

```text

 ↓

 ↓

```

That's one reason we're separating responsibilities now.

Should **Project Details** be responsible for directly containing all the implementation logic for:

```text

Task list
Individual task
```

* readability
* reuse
* complexity
* future changes

**Tell me what you would choose and why.**

And your reasoning is heading in the right direction.

## 8.1 Architectural Decision #1 — Component Composition

We'll structure `Project Details` as a **composition of meaningful components**, rather than making one giant component responsible for everything.

Conceptually:

```text
ProjectDetails
│
├── ProjectHeader
├── ProjectProgress
├── ProjectTaskList
│   └── TaskItem
└── ProjectActivity
```

The important part isn't the names. It's the **responsibility boundaries**.

### `ProjectDetails`

Its job is primarily to **coordinate the page**.

It shouldn't need to know every tiny UI detail.

### `ProjectHeader`

Responsible for presenting project identity and project-level actions.

### `ProjectProgress`

Responsible for displaying project progress.

### `ProjectTaskList`

Responsible for presenting the collection of tasks.

### `TaskItem`

Responsible for displaying one task and its relevant interactions.

### `ProjectActivity`

Responsible for displaying project-related activity.

---

## Why this is useful

Imagine we later change the task UI.

Without composition:

```text
ProjectDetails.jsx
    ↓
Change giant component
    ↓
Risk affecting everything
```

With composition:

```text
ProjectDetails
    ↓
ProjectTaskList
    ↓
TaskItem
```

We can work primarily inside the task-related components.

That's **separation of responsibility**.

---

# 8.2 But There's a Second Important Principle

Component composition doesn't mean:

> "Every piece of JSX becomes a component."

We create a component when the boundary is **meaningful**.

For example:

```jsx
<div>
  <h2>Project Progress</h2>
  <p>72% complete</p>
</div>
```

We don't automatically need:

```text
ProjectProgressContainer
ProjectProgressTitle
ProjectProgressText
ProjectProgressPercentage
```

That would be over-engineering.

Instead:

```text
ProjectProgress
```

is a meaningful unit.

# STEP 8 — APPLICATION ARCHITECTURE

## Architectural Decision #2 — State Ownership

We have:

```text
ProjectDetails
      │
      └── ProjectTaskList
              │
              ├── TaskItem
              ├── TaskItem
              └── TaskItem
```

A user completes one task.

That change can affect:

```text
Task status
    ↓
Project progress
    ↓
Dashboard statistics
    ↓
Activity
```

So putting the actual task data inside `TaskItem` would be a problem.

---

## 8.2 Where Should State Live?

The key principle is:

> **State should live at the lowest common parent that needs to coordinate that state.**

For our current project, that means the task data shouldn't belong to an individual `TaskItem`.

Conceptually:

```text
ProjectDetails
      │
      │ owns/receives project data
      ↓
ProjectTaskList
      │
      ├── TaskItem
      ├── TaskItem
      └── TaskItem
```

The task item receives the information it needs through props.

For example:

```text
ProjectDetails
      ↓ props
ProjectTaskList
      ↓ props
TaskItem
```

And when a task changes:

```text
TaskItem
   ↓ event
ProjectTaskList / parent
   ↓
state/data update
   ↓
UI re-renders
```

We're not writing this code yet. We're establishing the mental model.

---

# 8.3 Why Not Put State Inside `TaskItem`?

Imagine each task had its own independent state:

```text
TaskItem #1 → state
TaskItem #2 → state
TaskItem #3 → state
```

Now the parent doesn't necessarily know the actual overall task collection.

But we need the collection to calculate:

```text
3 / 5 tasks completed
```

and therefore:

```text
60% project progress
```

So the **collection-level information must exist above individual task items**.

---

# 8.4 Why This Matters in DevFlow

Suppose:

```text
Tasks:
5 total
2 completed
```

User completes another task.

We need:

```text
5 total
3 completed
```

Then:

```text
Project progress
40% → 60%
```

And potentially:

```text
Dashboard
Completed tasks: +1
```

The UI is therefore driven by shared application data.

This is why state ownership matters.

---

# 8.5 But We Don't Want One Giant Global State

Another beginner mistake would be:

> "Everything affects everything, so let's put all DevFlow state into one giant global object."

We won't do that.

We'll initially keep state **as close to where it is needed as reasonably possible**.

Later, if we discover that multiple distant parts genuinely need the same state, we'll evaluate whether it belongs in a shared state/data layer.

We don't need Redux/Zustand just because the application has multiple pages.

---

# 8.6 Architectural Decision #2 — Locked

```text
State ownership principle:

Keep state as close as possible
to the components that need it.

When multiple components need to
coordinate the same state, move it
to their appropriate common parent
or shared data/state layer.
```

For DevFlow:

```text
Individual task UI
        ↓
doesn't own the entire task collection

Task collection
        ↓
managed above individual TaskItem components
```

✅ **Decision #2 complete.**

---

# 8.7 Architectural Decision #3 — Data Flow

Now we need to establish how information moves.

React's basic model gives us:

```text
Parent
  ↓
Props
  ↓
Child
```

And user actions travel upward through callbacks:

```text
Child
  ↓ event/callback
Parent
  ↓
State/data update
  ↓
React re-render
  ↓
UI
```

For DevFlow:

```text
Project data
     ↓
ProjectDetails
     ↓
ProjectTaskList
     ↓
TaskItem
```

A task interaction:

```text
User clicks Complete
        ↓
TaskItem event
        ↓
callback
        ↓
parent/state update
        ↓
new task data
        ↓
React re-render
        ↓
updated UI
```

This is the same React you've already learned.

We're simply applying it to a real application.

---

# 8.8 Data Should Have a Clear Source

Another architectural rule:

> **Don't create multiple independent copies of the same source data unless there is a reason.**

For example, if a project has:

```text
tasks: [...]
```

we don't want:

```text
Project
  → tasks

Dashboard
  → completely separate copied tasks

Analytics
  → another copied task collection
```

and then manually try to keep them synchronized.

Instead, we want a clear source of truth and derive information where possible.

For example:

```text
Tasks
  ↓
completedTasks
  ↓
progress
```

This connects directly to the derived-state concepts you've already learned in React.

---

# 8.9 Architectural Decision #3 — Locked

```text
Data should have a clear source of truth.

Prefer deriving values from source data
rather than maintaining unnecessary duplicate state.

Use props/callbacks for normal component communication.
```

✅ **Decision #3 complete.**
